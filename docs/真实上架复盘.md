# 真实上架复盘：一次从 0 到 `imported` 的过程

> 2026-11-02，用真实店铺凭证（主体信息已隐去，CNY 结算）对 Ozon 发起真实商品导入。
> 目标不是"上架成功"，而是**看这条链路到底会在哪里断**。
> 结论：**17 个阻断点**，其中 3 个是"看似成功实则没落地"的假绿灯。

## 结论先行

| 项 | 结果 |
|---|---|
| API 链路 | **通**：`/v3/product/import` 返回 `task_id`，`/v1/product/import/info` 最终 `status=imported`、`errors=[]` |
| 商品是否创建 | **否**：回读 `statuses.is_created=false`、`status_name=Не продается`、`status_description=Не создан` |
| 卡在哪 | **没有图片**（`images: []`）。Ozon 要求图片是公网 URL，而本机所有公用图床均已不可用 |
| 已验证能力 | 类目树、属性、字典取值、仓库、币种、VAT、尺寸重量写入 —— 全部实测通 |

**「imported + errors 为空」不等于「商品已创建」。** 这是本次最重要的一条。

## 一、17 个阻断点

### 网络与协议层

| # | 现象 | 根因 | 正确做法 |
|---|---|---|---|
| 1 | `fetch failed: ConnectTimeoutError ...:443, timeout: 10000ms` | **不是网络不通**：curl 直连同一域名 11.35s 返回 401。Node undici 默认连接超时 10s 太短 | 所有 Ozon 调用设 `AbortSignal.timeout(60000)`。本机到 `api-seller.ozon.ru` 稳定 11s 左右 |
| 2 | 类目树子节点全是 `undefined` | 叶子节点是 **type 节点**，字段名是 `type_name`，不是 `category_name` | 遍历时 `n.type_name ?? n.category_name`；type 节点只有 `type_id`，没有 `description_category_id` |
| 3 | `/v1/warehouse/list` → 400 `obsolete method cannot be used` | 接口已废弃，不是权限问题 | 用 **`/v2/warehouse/list`**，返回 `{warehouses:[...]}`（注意不是 `result`） |

### 提交结构层

| # | 现象 | 根因 | 正确做法 |
|---|---|---|---|
| 4 | `invalid Request.Items.TypeId: value must be greater than 0` | `/v3/product/import` 必须要 `type_id`，我只给了 `category_id`（那是 v2 的字段集） | 同时给 `description_category_id` + `type_id` |
| 5 | `description_category_is_empty`（task 已 `failed`） | v3 认的字段名是 **`description_category_id`**；写成 `category_id` 会被**静默忽略**，不报字段错，只报"你没填类目" | 字段名必须是 `description_category_id` |
| 6 | `currency_differs_from_contract` | 店铺合同币种是 **CNY**（`/v1/seller/info` → `company.currency`），我按俄罗斯市场习惯写了 RUB | 先读 `/v1/seller/info` 拿 `currency`，不要假设当地货币 |
| 7 | `vat_not_zero_banned_in_country`：「你所在国家的 VAT 是 0%」 | **中国跨境卖家在 Ozon 的 VAT 是 0%**，不是俄罗斯的 22%（出口零税率）。按目的国税率填会被平台直接拒 | `vat: '0'`。这条推翻了"按俄罗斯 22% 计税"的直觉 |
| 8 | `missing_dimension`（连续 4 轮，换 3 种写法都失败） | **尺寸不是 `dimensions` 对象，是 item 顶层扁平字段**：`width` / `depth` / `height` / `dimension_unit`。而且用的词是 **`depth` 不是 `length`** | `{width:'250', depth:'300', height:'50', dimension_unit:'mm', weight:'400', weight_unit:'g'}` |
| 9 | `status=skipped`，改了内容也不生效 | Ozon 对同一 `offer_id` 判定"内容无变化"就跳过；而此前的改动恰好都是无效字段，于是永远 skipped | 换新 `offer_id` 验证一次，能区分"字段错"还是"幂等跳过" |

### 语义与回读层

| # | 现象 | 根因 | 正确做法 |
|---|---|---|---|
| 10 | 传的 `name` 没生效，线上变成 `Свитер`（毛衣） | 该类目按 `type_id` 自动生成展示名，与 Ozon 服装类目"名称由平台生成"的行为一致 | 名称仅供参考；搜索靠属性与 4191 描述 |
| 11 | `/v3/product/info/list` 查询返回 0 条 | `filter` 必须放**顶层** `offer_id` 数组，不能嵌套成 `filter.offer_id` | `{offer_id:['xxx']}` |
| 12 | 回读 `dimensions: {}`、`weight: null` | 与 #8 同源：字段没被接受，线上就是空 | 用顶层扁平字段重提后再回读确认 |
| 13 | `/v1/analytics/data` → 429 | **不是无权限**，是每秒限流 | 加间隔重试；该接口只返回自己店铺数据（店铺 0 商品时为空） |
| 14 | `/v1/search/products`、`/v1/category/search` → 404 | 这两个端点不存在 | 市场竞品数据不能靠卖家 API 拿 |

### 素材与外部服务层

|---|---|---|---|
| 15 | Ozon 前台 `www.ozon.ru` → 「Похоже, нет соединения」 | 本机 IP 被 C 端风控挡；API 域名与 C 端域名策略不同 | C 端竞品数据本机拿不到，需换网络或代理 |

## 二、三个「假绿灯」

这三条比报错更危险，因为报错会让人停下，假绿灯会让人以为做完了。

| 假绿灯 | 真相 |
|---|---|
| HTTP 200 + `task_id` | 只代表"任务已排队"，不代表参数正确 |
| `status=imported` | task 级状态。**第一次 imported 时 errors 里有 3 条 `missing_dimension`**，商品照样没创建 |
| 回读有 `id`、有 `price` | 商品记录存在 ≠ 商品创建成功。判据只有一个：`statuses.is_created === true` |

**验收红线**（写进脚本，不靠人看）：
`is_created === true` 且 `task.errors.length === 0` 且 `product.errors.length === 0`，三者同时成立才算落地。

## 六、续：图床解决后，商品真的上架了（2026-11-02 晚）

### 6.1 图床：用卖家自有 COS，不走公用图床

在 `~/.workbuddy/skills/ozon-women-upload` 里全量检索，找到反复出现 103 次的自有图床：

```
https://<卖家自有 COS 域名>/img/misc/
```

实测两张图均为 `HTTP 200 / image/jpeg / 1200×1600`（3:4），公开可读、无需签名。
（具体域名与 bucket 已隐去：公开仓库里出现卖家图床地址等于给出可盗链的目标。）

**路径约定**：`/img/misc/<序号>-<类型>-<n>.jpg`，类型区分 `flat`（白底）与 `model`（模特）。同一目录里也有 `az-xxxx-detail_01_01.jpg` 这种按款号命名的详情图。

顺带印证了一条旧教训：公用图床即使能传，也**不该长期托管主图**（历史上出现过图床不可达导致 Ozon 拉图失败 `pics_http_error`）。

### 6.2 补上图片之后又冒出两个错

| # | 现象 | 根因 | 正确做法 |
|---|---|---|---|
| 18 | 带图提交后 `task=imported`、`errors=[]`、`images=5` 已写入，但 `is_created=false` | 商品创建是**异步**的：此刻 `status=offer_validated`、`status_description=Создается`。此时去设库存会得到 `PRODUCT_IS_NOT_CREATED` | 轮询 `statuses.is_created`，**实测约 45 秒**后变 `true`、状态转 `price_sent` |
| 19 | 提交 5 张图，回读只剩 4 张 | Ozon 审核会剔除重复/低质图（旧经验里也有「10 张传入→线上留 7+1」） | 提交时多给 1–2 张冗余；`images` 计数不要按提交数写进验收判据 |

### 6.3 最终成功链路（可复现）

```
1. 方向验证   market:scan → HS 6110 → 俄罗斯进口 $1.02B、中国占 31.3% → 方向成立
2. 属性取数   类目 200000933 / type 93214；6 个必填属性 + 字典值
3. 组装       顶层扁平尺寸（width/depth/height/dimension_unit）+ 重量
              price 199 CNY / vat 0 / currency CNY
              images 指向自有 COS（5 张，含 2 张白底 + 3 张模特）
4. 提交 v3/product/import → task_id
5. 轮询 v1/product/import/info → imported / errors=[]（约 10 秒）
6. 轮询 v3/product/info/list → is_created=true（约 45 秒），状态 price_sent
7. 设库存 v2/products/stocks → updated=true（必须在第 6 步之后）
8. 回读确认  has_stock=true / present=999 / sku 已生成 / images 留存 4 张
```

**L2 结果**：`product_id 6831123035`，SKU `6218806480`，状态 `price_sent`，库存 999（FBS），价格 199 CNY，4 张图。商品在 Ozon 侧已创建并可售。

### 6.4 判据修正（第二次）

第一版写「`is_created === true` 且两层 errors 为空」，仍不够。完整判据是四条：

1. `task.status === "imported"` 且 `task.errors` 为空
2. `statuses.is_created === true`
3. `stocks.has_stock === true` 且 `present > 0`
4. `images` 实际留存数 ≥ 平台最小张数

只满足前两条时，商品在后台**建出来了但不可售**（`Нет на складе`），跟没上架在使用上没区别。
