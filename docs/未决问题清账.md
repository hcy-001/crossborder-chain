### 10.1 关键洞察：平台的错误码表，就是一份完整的准入规则清单

`POST /product/create` 的文档页里，除参数说明外还有一张 **Error Code 表**。那张表不是"异常处理参考"，是**平台把所有拒绝原因逐条列了出来**：

| 错误码 | 原文 | 等价规则 |
|---|---|---|
| 4160 | The max length of Multi title for locale can not exceed 255 **bytes** | 标题上限 255 **字节**（中文约 85 字，不是 255 字） |
| 4169 | Upload a maximum of 8 pictures | 最多 8 张图 |
| 4164 | The package weight exceeds 40kg | 包裹 ≤ 40kg |

| 4129 | Special characters are not allowed: `^~<>\|` | 五个禁用符号 |
| 4115 | The CPV attribute is not one of the options provided by the category | 属性值必须在下拉选项里 |
| 4157 | The discount price must be cheaper than the regular price | 促销价必须低于原价 |
| 4139 | Main image is require | 必须有主图 |

### 13.3 Amazon 的标题"冲突"解决了：不是冲突，是两段式

上一轮我把它记成"两个站点打架、保持并列"。这一轮从 Amazon SP-API 的 llms.txt 里找到 `submit-modular-titles`：

| 字段 | 用途 | 上限 |
|---|---|---|
| `item_name` | 品牌 + 品类 + 关键特征 | **≤75** |
| `title_differentiation` | 逗号分隔的差异点（Item Highlights） | **≤125** |

**合计 200**。而且：`item_name` 超过 75 时，**亮点字段直接提交不上去**。2026-07-27 起对所有非媒体类商品生效。

所以两个站点页面一个写 200（合计）、一个写 75（分段），口径不同而已。校验器现在会在主标题超 75 时给"拆到 Item Highlights"的提示，而不是判违规。

**这条是 `llms.txt` 这个入口带来的** —— 之前所有 HTML 路径都拿不到。

### 13.4 「官方没规定比例」怎么处理：不猜，也不因此瘫痪

Яндекс Маркет 的图片要求只给最小尺寸，**不规定宽高比**。

之前的逻辑是"没有比例就拒绝出包"（怕猜着裁图）。但这样一来，一个 13 条事实全核实过的平台会因为"官方没规定"而完全用不了 —— 这是把严谨变成了瘫痪。

改法是加一条 `image.ratio_policy: "preserve"`：**保持母版原比例直接出图，不做任何几何变换**。平台没禁止的比例不算违规，不裁也不会丢画面。

实测：9 张图原样出、`crops=0`、通过项 `ratio_preserve_source_copy`。

判据是「**不裁切永远比猜着裁安全**」：裁错了不可逆，不裁最多是画面不是最优构图。

## 十四、Wildberries 打穿了：走错门走了五轮（2026-11-02）

### 14.1 错在哪：一直敲的是开发者文档，卖家文档在另一个门里

前几轮我反复试 `dev.wildberries.ru`（开发者 API 文档），每次都被 IP 级封禁（498 + 「Подозрительная активность」）。结论写成"文档站封了，只能等账号"。

**真正的问题是走错了门**。WB 的卖家规则文档在：

```
https://seller.wildberries.ru/instructions/cn/ch/
```

- `seller.` 域名**没有被封**（只有 `dev.` 被封）
- 路径里的 `cn/ch` = **中国站 / 中文**
- 文章页是 **React Server Components**，正文在流式 payload 里 —— curl 能拿到 772KB 的 HTML，但要用浏览器取 `innerText` 才干净

**这条是"搜索引擎索引"给的线索**：搜「Wildberries 新手卖家指南 中文版」时，第一条结果就是 `seller.wildberries.ru/instructions/ch/ch/material/A-292`（《如何创建商品》）。

## 十五、清掉最后两个待核平台 + 一个会毁图的缺陷（2026-11-02）

### 15.1 Amazon：现行原文一直拿得到，只是入口换了

前几轮把 Amazon 的 8 条图片事实全标成 `candidate`，理由是「帮助页有登录墙，只有 2022 年存档」。这一轮发现两件事：

**① G1881 已经不是图片指南了。** 2025-03-07 的快照里，G1881 的内容是「Intellectual Property Policy for Sellers」——Amazon 复用了这个 ID。所以 2026-09-28 的快照抓回来是登录墙营销页，不是被拦，是**这个 ID 指向的东西变了**。

**② 搜索引擎索引里就有现行全文。** 搜「Amazon product image requirements 85% 1600」时，第二条结果直接是 G1881 的当前完整正文（含 technical requirements 全文）。需要的信息一条不缺。

拿到的原文（现行版）：

> All images must meet the following requirements: **500 to 10,000 pixels on their longest side**; Provided in JPEG, TIFF, PNG, or non-animated GIF; Clear with no pixelation
> We prioritize images larger than **1,000 pixels** on the longest side to allow for zoom
> We recommend having **at least six images and one video**
> Show the product as **85% of the image**；纯白背景 RGB 255,255,255

**最关键的修正：官方根本没有规定宽高比。** 我们之前按 1:1 裁图，是把二手说法当成了官方要求。这条错误的代价是每张服装图被切掉上下各 12.5%。

同时撤掉一条错事实：`image.max_count = 7`（二手转述）。官方只说「至少 1 张」「建议 6 张 + 1 视频」，**没有给上限**。

结果：Amazon 从 4 final / 8 candidate → **19 final / 2 candidate**，改为原图直出。

### 15.2 Lazada：比例口径确实拿不到官方原文，但风险性质变了

把能试的都试完了：

| 入口 | 结果 |
|---|---|
| `open.lazada.com` 的 `/image/upload` 文档页 | 200，但只有 API 目录；详情页跳登录 |
| Lazada 各站点 `sellercenter.*/help` | 全部 302 到登录 |
| `university.lazada.com` | 阿里系 SPA，需登录 |
| `www.lazada.cn`（中国招商站） | 200，但「商家学习中心」也是 university 那个 |
| 前台商品页抓图片 URL | SPA，拿不到 |

结论：**Lazada 的 800×800 / 1:1 在公开域只有多源转述，没有官方原文。**

但这一轮改了 1:1 的几何处理之后，这个「candidate」的风险性质变了：

- 旧做法（中心裁切）：口径错一次 → 裙摆领口被切掉，**不可逆**
- 新做法（补白边）：口径错一次 → 主体显小一点，**不违规**

所以判定不该再是「candidate 就一律待核」。现在的口径是：**1:1 + 补边 → 可出包，但注明尺寸下限仍待后台确认**。

### 15.3 一个会毁图的缺陷：1:1 平台在中心裁切

三个平台（Shopee / Lazada / TikTok Shop）都在把 900×1200 裁成 `[0,150,900,900]` —— **切掉上下各 150px，画面 25%**。

对服装主图这是致命的：裙摆、领口、腰部细节正好在这两条带上。而这三个平台同时要求「商品完整可见」和「纯白底」。

改成 `contain-pad-white-v1`：等比缩放到 675×900，左右各补 112/113 纯白边，输出 900×900。

- 内容区 `[112,0,675,900]`，**零像素丢失**
- 补边色 `#FFFFFF`，满足白底要求
- 台账里 `mode: contain_pad` + `canvas: [900,900]`，可追溯
- 测试断言：内容区必须**逐字节等于**「原图缩放到 675×900」的结果

**副产品**：`crop_safe` 这个字段失去意义了。原来它标记「这张图不能裁所以跳过」，现在不裁了，所有 9 张都出图。

### 15.4 上 GitHub 时被 clone 打回两次

第一次 commit 后从干净目录 clone，**14 个测试失败、测试数从 361 掉到 338**。

根因：`.gitignore` 里写了 `package/`（没有前导斜杠）。git 的目录规则没有前导斜杠时会匹配**任意层级**，于是 `core/package/` 被整个忽略——clone 下来直接 `ERR_MODULE_NOT_FOUND: core/package/assemble.mjs`。

修法：所有「只指仓库根目录」的规则都加前导斜杠（`/package/`、`/runs/`、`/assets/`、`/input/*`）。

第二次 clone：**361/361、7 门、evals 3/3、quickstart 跑通**。

**教训**：本地跑绿不等于仓库能用。`git clone` 到空目录跑一遍，是唯一能发现「文件没提交」的手段——它和 `npm test` 是两件事。

### 16.7 实际的字节差

先生手搜出的地址栏：

```
https://s.1688.com/selloffer/offer_search.htm?keywords=%D5%EB%D6%AF%A3%AC%BF%AA%C9%C0&spm=...
```

`%D5%EB%D6%AF` = 针织，`%A3%AC` = **全角逗号**，`%BF%AA%C9%C0` = 开衫 —— 这是 **GBK**。

同一句话用两种编码：

| 编码 | 结果 |
|---|---|
| GBK | `%D5%EB%D6%AF%A3%AC%BF%AA%C9%C0` |
| UTF-8 | `%E9%92%88%E7%BB%87%EF%BC%8C%E5%BC%80%E8%A1%AB` |

服务器按 GBK 解 UTF-8 的字节，得到的是乱码关键词 —— 于是返回「随便什么东西」，页面**看起来有结果**，所以不报错。

### 16.8 修法与证据

Node 内置 `TextDecoder('gbk')` 只能解码，没有编码器，也没有 iconv-lite。**反过来用解码器建编码表**：遍历 GBK 双字节空间（lead `0x81–0xFE` × trail `0x40–0xFE`），逐个解码，能解出单字符的就登记「字符 → 字节」。23,939 字，**25ms**，一次性缓存。

新增 `channels/source/ali1688.mjs`：

```js
encodeGbk("针织，开衫")  // === "%D5%EB%D6%AF%A3%AC%BF%AA%C9%C0"  ← 与先生手搜的地址逐字节一致
buildSearchUrl(keyword)   // 唯一允许拼 1688 搜索 URL 的地方
```

新增 `scripts/scan-1688-quotes.mjs` + `npm run quotes:1688`，第一次跑就拿到：

```

GBK query：%D5%EB%D6%AF%A3%AC%BF%AA%C9%C0
报价 55 条
  最低 20 ｜ P25 29.7 ｜ 中位 39.0 ｜ P75 58.5 ｜ 最高 146
```
