# 模块替代评估：先怀疑有没有，再决定换不换

> 方法：把链路拆成 8 块，每块先问「这事有没有现成的、更权威的实现」，查了再决定。
> 结论分三类：**换**（用现成替代）、**留**（自研更合适，写明理由）、**待换**（该换但现在缺条件）。

## 一、总表

| 模块 | 有更优现成方案吗 | 决定 | 理由 |
|---|---|---|---|
| 1 选品信号 | 有（卖家的选品工具/服务商） | **留，已接** | 自建抓取要面对反爬与合规，不如吃现成工单。当前就是从选品技能取 `sourcing_ticket` |
| 2 候选打分 | 没有标准品 | **留（自研）** | 打分维度是业务定义，没有公认实现；自研的好处是确定性、可复算 |
| 3 市场画像 / 人群 | 没有开源等价物 | **留（自研）** | 需要结构化输出 + 拒绝路径，通用框架给不了 |
| 4 商品图生成 | 有（现成图像模型 / ComfyUI 本地部署） | **留，走 API** | 已接通用图像接口；本地 ComfyUI 省单价但要 GPU 与运维，当前阶段不划算 |
| 5 尺码映射 | **部分有**：平台只管「字段怎么填」，不管「通用表怎么映射」 | **留（自研）+ 修正一处** | 跨平台映射没有开源库；但**尺码表本身有官方格式**（见下） |
| 6 定价 / 毛利 | **有**（大量开源毛利计算器，公式一致） | **不自造，已对齐** | 见第二节：我原来的口径是错的，已按公开公式改成分母法 |
| 7 平台校验 | **有**（平台官方 import 端点会给真实拒绝原因） | **待换** | 需要写权限；当前只读账号拿不到 |
| 8 打包 / 门禁 | 无 | **留（自研）** | 这是本项目最硬的部分，没有替代必要 |

## 二、毛利：我原来的算法是错的（已修）

查到的公开口径（多个开源计算器与教材一致）：

```
毛利率(%) = (售价 − 成本) / 售价
加成(%)   = (售价 − 成本) / 成本
互相换算：margin = markup / (1 + markup)，markup = margin / (1 − margin)
由成本反推售价：P = 成本 / (1 − 毛利率)
```

**我原来的实现错在基数**：把佣金、税、手续费当成"成本的百分比"加上去。但这三项都是**按售价抽**的（佣金按成交额、手续费按流水、VAT 含在售价里）。基数用错，售价会被系统性低估。

实测差额（一件 67 元采购 + 33 元运费，佣金 18% / 税 6% / 手续费 2% / 目标毛利 30%）：

| 算法 | 售价 | 佣金实际应为 | 差价 |
|---|---|---|---|
| 旧（按成本加成） | 180.00 CNY | 18.00（算少了） | — |
| 新（分母法） | **227.27 CNY** | 40.91 | **少算 47.27 CNY ≈ 573 RUB/件** |

按旧价卖，每件亏约 573 卢布。现在改成：

```
保本价 P0 = 固定成本 / (1 − 佣金率 − 税率 − 支付费率)
目标价 P  = 固定成本 / (1 − 佣金率 − 税率 − 支付费率 − 目标毛利率)
```

并且回执里给**自洽明细**：固定成本 + 佣金 + 税 + 手续费 + 利润 = 售价，误差 ≤ 0.03，毛利率精确落在设定值（有测试锁定）。

不可达时明确报 `margin_unreachable`（费率+毛利 ≥ 100%），不给一个假价。

## 三、尺码：有一个我该换但换不了的地方

平台的**尺码表**不是一个自由文本，`Одежда / Платье` 类目里它是独立属性 `#13164 Таблица размеров JSON`，值是 JSON 字符串，官方有专门的知识库文章规定结构。

我现在的做法：尺码**值**（`#4295`）按官方规则生成 —— 连续 4 个及以上折叠成「通用」，其余用 `;` 串（`42;44` 显示为 42–44）。规则与依据在 `regions/RU/sizing.json` 的 `size_value_rules`，判定在 `core/sizing/rules.mjs`。

尺码**表**（`#13164`）仍未产出 JSON，但原因变了：不是"没查到"，而是**官方公开文档里根本没有这份 JSON 的结构**。官方《服装和配饰的尺码》只说了一句："部分卖家可使用处于测试模式的新工具，其中：尺码表是必填属性。请先选择尺码表：可供选择的尺码取决于所选尺码表。" —— 也就是"从官方通用表里选一张 + 填码"，而不是自己写结构。

> 中国卖家站流传的 `country / category / size_type / measurements` 那套字段，与官方构造函数截图里的列（`RU / INT / Обхват груди / Объем талии / Объем бедер`）对不上，是编的，不采用。

下一步（有账号就能做）：在后台尺码表编辑器里复制一次 JSON 出来，把结构固定成模板，让 `size-card` 同时产出一份可粘贴的 JSON。在那之前，交付说明只写"选哪张通用表 + 填哪些码"，不假装能生成表结构。

## 四、WB 已按你的实际情况处理

`regions/RU/profile.json` 新增 `platform_accounts`：

```json
"ozon": {"status": "active"},
"wildberries": {"status": "no_account", "note": "卖家无 WB 账号（2026-10-29 确认）"}
```

链路只对 `active` 平台出投影；WB 直接跳过并在回执/回执文档写明「跳过 wildberries（无账号）」。实测包内 `platforms/` 只剩 `ozon` 一个目录。

好处：不再产出一堆"填不了的空壳"，回执也不会假装 WB 已就绪。

## 五、结论

- **定价是必须换的**：换成公开口径的分母法。这不是风格问题，是"按旧价卖会亏"级别的错误。
- **尺码值规则是必须补的**：连续 4 个及以上要折叠成「通用」，成码有步长与区间 —— 按官方原文补，已落到配置与代码里。
- **尺码表 JSON 仍是待换的**：官方没有公开结构，取不到就不写。
- **其余六块维持自研**：不是因为我更喜欢自己写，而是替代品要么不存在（打分、判别、门禁），要么需要额外资源（本地 GPU、写权限），要么会引入新的不确定性（第三方抓取）。
