# 三视角自评：它够格吗（2026-10-29）

> 规则：先给反方论证，再给结论；结论标 L0/L1/L2。**不给自己发好评。**

## 一、评委视角：能到什么名次，取决于评审看什么

**如果评审看「可复核性」——够格。**
我这套东西最硬的地方不是功能多，是每个结论都能被追问到底：

- 10 个判别点，每个都有接受路径、拒绝路径、同形回退，且回退值必须过同一份 schema（`G3-JUDGE` 机械门强制）。
- 证据等级从台账反算，不靠自评：0 次模型返回写不出 L2。
- 7 道机械门 + 361 项测试，`npm run selfgrade` 任一项不过就 exit 1。
- 平台事实不是我猜的：Ozon 尺码属性 `#4295 Российский размер`（必填、集合型、字典 835）与 5 项必填属性，都是用 Seller API 只读实测拿到的（L2）。

**如果评审看「闭环」——不够格。** 平台侧**零提交、零回读**。所有"能不能上架"都是推断。这是根本短板，且我一个人解决不了。

⚠️ 反方：如果这个判断错了，最可能错在——我把"可复核"当成了稀缺品，而评委可能更看重"跑起来像不像真生意"。那就需要演示脚本与一页商品卡，而不是更多台账。

**最致命的一条**：真实跑通的 SKU **只有 1 个**。样本量 1 的系统，任何"稳定"的说法都站不住。

## 二、用户视角：愿不愿意用第二遍

**第一遍能用，第二遍才会见真章。** 这轮把最扎人的地方改掉了：

- 原来让你改 JSON 才能确认尺码字段 → 现在一条 `npm run sizing:confirm`，四个问题、回车即用。
- 原来跑完只给一张表 → 现在给「下一步」（打开哪个 handoff）与「还缺什么」（价格缺哪几项、哪个平台尺码填不了）。
- 原来 22 个问题像工程师问工程师 → 现在每条都有「怎么写」的样例，且**任何必答项都可以写 `unknown`**（明确表态，系统如实降级，不逼你编数字）。
- 原来问卷问了成本、重量、尺码表，代码却只读工单 → 现在**问卷优先、工单兜底**，回执记 `sources: {cost: "intake"}` 可查。

⚠️ 反方：如果这个判断错了，最错在——**问卷还是太长（27 项）**。第一次用的人很可能答到一半就烦。真正的解法是把 14 个必答项拆成"开箱必答 6 项 + 其余可后补"，但这会削弱"缺项不出价"的严格性，我暂时选择严格。

**产物形态**：JSON + CSV + Markdown 之外，出包时会写一份 `package/<sku>/onepager.html` —— 母版图、定价、尺码、平台属性、合规、降级一页看完，数据全部来自包内文件，不含新结论。

## 三、商人视角：这笔钱敢不敢投

**不敢按现在的形态投。** 三个硬问题：

1. **没有毛利模型**。系统算的是"成本项合计"（采购+运费+佣金+税+手续费），**没有售价、没有目标毛利、没有 break-even**。商人最关心的那一栏不存在。
2. **样本 1**。一个 SKU 跑通不代表能批量；退货率、审核通过率、实际转化，一个数据都没有。
3. **看不到钱**。图像模型单价未查证，回执只记 token，**单包成本说不出来**。

⚠️ 反方：如果这个判断错了，最可能错在——早期阶段本来就该先验证"能不能过审、能不能出图"，毛利模型属于规模化之后的事。这个反驳成立，但至少要有 break-even 一条线，否则连"这个价能不能卖"都答不了。

## 五、如果只能再做三件（按对"够格"的贡献排序）

1. **把字典型属性的取值填对**（P0）：映射表已建、必填覆盖 6/6 已达成，卡在 `Тип` 这类字段要填字典项而不是自由文本。判据：`npm run check:attrs` 无 `⛔`。
2. **第二个真实 SKU**（P1）：换个品类跑一遍，看链路是否只在女装成立。判据：两个 SKU 全部 9 图 + 尺码 + 平台投影齐备。
3. **平台侧一次真实提交与回读**（P1）：打破"零提交、零回读"。判据：一条平台返回的拒绝原因或上架成功回执，且能对上我们的预检结论。

## 六、结论

**工程上，这是一份可以交给乙方、经得起逐行追问的东西；商业上，它还不是一个能赚钱的系统。**

我不会用"300 行代码 + 100 分自评"糊过去：自评只覆盖我定义的七项，而那七项里没有"能不能卖出去"。
