## 二、写权限能不能确认

**不能，靠只读探不出来。** 我没有调用改价 / 改库存 / 导入商品这类端点 —— 一旦调用就是真改线上。

判断方式只有两个：
1. 卖家后台 → 设置 → Seller API → 该密钥的**权限勾选列表**（你自己看一眼即可）；
2. 用一条**可回滚的最小写**去试（例如给一个不存在的 SKU 改价，预期 404 而非 403）—— 有风险，不建议默认做。

## 三、"让用户直接给自己的 API"是否可行

**技术可行，但不能一步到位。** 分三档，只有第一档现在就该做：

| 档 | 能做什么 | 前置条件 | 建议 |
|---|---|---|---|
| A 只读校验 | 用用户 key 查类目属性、核对必填项、查价格库存、拉报表 | 用户给 Client-Id + Api-Key（只勾读权限） | **立刻可做**，风险低 |
| B 写入执行 | 改价、改库存、提交商品 | 二次人工确认 + 字段白名单 + 变更前后快照 + 可回滚 | 做，但必须先有 A 稳定运行 |
| C 全托管上架 | 自动提交、自动跟价 | 平台风控、责任界定、售后 | **不做** |

### 为什么不能"用户一给 key 就直接上架"

1. **一个 key 能改的是真金白银**：错一个字段就是错价，卖出去就是亏损，且平台有风控；
2. **多租户密钥是负债**：一旦落盘明文，泄露等于把店铺交出去；
3. **责任边界**：我们代提交，出错谁承担？现在没有答案。

## 四、如果要做 A 档（只读），必须落地的 5 件事

1. **最小权限**：只要求用户勾"商品读 / 价格读 / 报表读"，不要 Admin。
2. **密钥不落明文**：只用进程内存 + 环境变量注入；日志、回执、证据文件里一律出现 `Client-Id 483***` 这种掩码（现有脚本已是如此）。
3. **不写日志**：请求日志只记端点与状态码，不记 header。
4. **可撤销**：界面上一键解除，解除后本地立即丢弃；用户随时可在后台删 key。
5. **说清用途**：接入页写明"我们只用它读取，不会修改你的商品"，且这一点有代码约束（只读端点白名单，写端点在 A 档直接不实现）。

## 五、这件事对当前交付意味着什么

- 这次实测把"平台事实"从"二手推测"提到了 **L2**（官方接口返回）；
- 也把"能不能上架"这个问题问实了：**店铺 0 商品，说明上架从来没发生过**；
- 因此下一阶段的重点不是继续加功能，而是：**用只读档把"这包能不能过审"做成可验证的检查**（必填 6 项覆盖、图片规格、标题长度），再把写权限作为独立一步引入。
